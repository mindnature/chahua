# Chahua Pipeline｜自然材料拼贴海报与视频流水线

## 0. 默认运行策略：FAST

默认使用 `FAST` 成功路径，不把每一步都按故障诊断流程执行。

目标只有三个阶段：

1. **SELECT**：当天联网搜索 2–3 组候选方向，选出最佳 1 张并保存到 `D:\picture`。
2. **POSTER**：在 ChatGPT 中生成上下对照海报 → 发送“去掉上半部分。” → 下载最终拼贴图 → 生成并保存小红书标题与简介。
3. **VIDEO**：在 Gemini 中严格按顺序进入视频模式、配置模型和画幅、上传最终拼贴图、注入完整提示词、生成并下载视频。**视频成功下载后立即结束，不再做抽帧、内容 QA、播放检查或二次分析。**

默认：

```text
max_items = 1
speed_profile = FAST
video_stop_after_download = true
auto_retry_quality = false
```

除非用户明确要求批量，否则不得扩大到多张图片或其他目录。

---

## 1. 固定目录与最小状态

```text
D:\picture
D:\picture-output
D:\picture-output\video
D:\picture-output\.chahua-state.json
```

状态只在“阶段边界”写入，不要每点一次按钮就更新一次文件。

最少记录：

- `run_id`
- `date`
- `stage`: `select | poster | video | done | blocked`
- `source_image`
- `source_url`
- `selection_score`
- `poster_final_image`
- `xiaohongshu_text_file`
- `video_input_image`
- `video_downloaded_file`
- `last_error`

### 状态写入时机

只在以下节点写入：

1. SELECT 最终图片已成功保存；
2. POSTER 最终拼贴图与小红书文案已成功保存；
3. VIDEO 视频已成功下载并归档；
4. 出现阻断性错误。

浏览器中的“已点击、已聚焦、已打开菜单”等瞬时动作不要写状态。

恢复运行时先检查状态文件和实际产物路径。文件存在且有效时，从下一未完成阶段继续，不重复打开旧聊天做无意义核验。

### 命名

```text
YYYYMMDD_<scene-keyword>_source.<ext>
YYYYMMDD_<scene-keyword>_collage.<ext>
YYYYMMDD_<scene-keyword>_xiaohongshu.txt
YYYYMMDD_<scene-keyword>_making.mp4
```

不得覆盖原图；同名时追加 `_02`、`_03`。

---

## 2. 懒加载能力检查

不要在流程开始时同时检查 ChatGPT 和 Gemini，这会制造多余页面访问。

启动时只检查：

1. 桌面控制能力可用；
2. 本地目录可读写；
3. Chrome 可启动。

到 POSTER 阶段时才检查 ChatGPT；到 VIDEO 阶段时才检查 Gemini。

某能力门失败时写入 `stage=blocked` 和 `last_error`，停止。不得静默替换网站、模型或画幅。

# 第一阶段：SELECT｜高速选图

## 3. 搜索方式

一次发起 2–3 组候选方向，优先在同一轮图片搜索中并行获取，不要逐方向串行搜索、逐图打开十几个页面。

候选题材：

- 城市天际线 / 黄昏城市
- 湖景 / 海边 / 河岸 / 倒影
- 山川 / 云海 / 晨雾 / 雪山
- 田野 / 梯田 / 农作 / 乡野慢生活
- 雪景街道 / 雨后街道 / 秋日街道
- 古镇 / 巷弄 / 老街 / 骑楼 / 石板路
- 森林 / 林间小路
- 有行人、劳作身影、自行车、车辆等点缀的生活场景

禁止：动物特写、单一植物特写、纯人物肖像。

## 4. 选片标准

候选必须满足：

1. 风景或街景构图为主体；
2. 主体清楚、层次分明，适合用自然材料重构；
3. 有意境或叙事感；
4. 色彩关系鲜明；
5. 有明确重心与留白；
6. 横竖均可。

直接淘汰：主体过碎、密集无层次、纯大头人像、单一花草/动物特写、严重水印、明显低清、无法获取公开原图。

### 快速评分

仅对最有希望的少量候选评分，不必给所有搜索结果建表。

6 项各 0–5 分：

- 场景适配度
- 手工拼贴可重构性
- 意境 / 叙事感
- 色彩辨识度
- 重心与留白
- 清晰度与可下载性

满分 30，优先 `>=24`。最高分不足 24 时再补搜索 1 轮。

## 5. 下载

只对最终胜出图执行深度动作：

1. 打开来源页 / 原图；
2. 确认不是缩略图；
3. 下载最高可用质量；
4. 保存到 `D:\picture`；
5. 用文件存在 + 文件大小检查确认下载成功；
6. 写入 SELECT 状态后立即进入 POSTER。

不要对未入选候选反复打开原图页、截图、记录详细元数据。

# 第二阶段：POSTER｜ChatGPT 制图

## 6. 浏览器原则

- 使用可见文字、ARIA、语义控件定位，不用固定坐标。
- 不做完整 DOM 扫描；优先查找当前动作所需的目标控件。
- 不使用长时间固定 sleep；等待生成时用 3–5 秒级状态轮询。
- 页面正常时不要截图；只有元素定位失败或状态矛盾时才截图诊断。
- 同一阶段尽量停留在同一标签页，不来回切换。
- 技术性操作失败允许自动重试 1 次。

## 7. ChatGPT FAST 路径

严格按以下顺序：

1. 打开 / 切换 Chrome，进入 `https://chatgpt.com/`。
2. 新建聊天。
3. 进入“创建图片”。
4. “添加照片和文件” → 上传当前 `source_image`。
5. 读取 `prompts/poster.md` 的主海报提示词并完整发送。
6. 仅等待“本轮图片生成完成”这一条件，不做中间截图或反复检查细节。
7. 在同一对话发送：`去掉上半部分。`
8. 等第二张图生成完成。
9. 下载第二张图；记录点击下载前时间，立即用 `archive-latest-download.ps1 -Kind collage` 归档到 `D:\picture-output`。
10. 只做**结构性快速检查**：文件存在、大小非 0、当前下载确实来自第二次生成。不要做耗时审美 QA。
11. 在同一对话发送：`给我一个小红书笔记版本的五个字以内的标题和图片简介，简介要排版精美符合小红书特色。`
12. 保存返回文本到 `_xiaohongshu.txt`。
13. 写 POSTER 状态，立即进入 VIDEO。

### 只有误解时才兜底

“去掉上半部分。”第一次必须用用户指定短指令。

只有结果明显仍有上下两部分或重新设计时，才补发：

> 仅保留上一张图的下半部分自然材料拼贴成品；删除整个上半部分照片区域。保持下半部分的主体、构图、文字、材料、色彩和细节不变，输出为单张 3:4 竖版成品图，不要重新设计。

不要为了保险无条件生成第三张图。

# 第三阶段：VIDEO｜Gemini 视频

## 8. 视频阶段是最高优先级顺序约束

过去的失败已经验证：**顺序错误会让 Gemini 把请求当普通文本对话，或者在模型切换后丢失视频模式。**

正常路径必须一次完成，不跳步：

1. Chrome 新建标签页，打开 `https://gemini.google.com/app`。
2. 新建聊天。
3. 先进入 `Create video / 视频` 模式。
4. 设置 **9:16 纵向**。
5. 选择 **3.8 Flash** 并开启 **Extended Thinking**。页面若合并显示为 `Flash 扩展`，视为配置成功。
6. **只做一次配置后总检查**：确认视频模式仍处于激活状态、模型为 3.8 Flash + Extended Thinking、画幅为 9:16。
7. 只有第 6 步通过后，才上传 `poster_final_image`。
8. 上传后只确认附件已经出现，不做额外截图。
9. 点击提示输入框，使用可靠的真实输入方式（优先 `bu.type` / 键盘输入）注入 `prompts/video.md` 全文。
10. **发送前必须验证提示词确实进入输入框**：文本长度明显大于 100 字符，并能读到开头与结尾的内容。若为空，禁止发送。
11. 点击发送。
12. 等待 Gemini 出现“视频已准备好”或等价完成状态，并出现可下载视频。
13. 点击下载。
14. 用点击下载前记录的时间作为 `Since`，立即运行 `archive-latest-download.ps1 -Kind video`，归档为 `D:\picture-output\video\YYYYMMDD_<scene-keyword>_making.mp4`。
15. 只检查：目标 `.mp4` 已存在且大小非 0。
16. 写入 `stage=done`，**立即结束整个 Skill**。

## 9. 视频成功后的禁止动作

用户已明确：Gemini 成功生成并下载的视频就是最终结果。

因此默认不得再执行：

- 抽帧；
- ffmpeg 内容分析；
- 播放视频检查；
- 逐秒 QA；
- 对最后一帧做像素比对；
- 回到 Gemini 查看是否还有“Refining”版本；
- 因为审美或内容猜测自动生成第二版；
- 下载后再截图验证页面。

这些动作只在用户**明确要求视频 QA**时才执行。

# 10. RECOVERY｜仅失败时启用

FAST 路径中的某一步失败后，才进入 `RECOVERY`。不要让所有成功任务都承担诊断成本。

### UI 定位失败

1. 重新查询目标语义控件一次；
2. 仍失败才截图 / 检查页面；
3. 修复后回到当前步骤，不重跑整个阶段。

### Gemini 特殊恢复

若发送后 Gemini 回复“我是一个语言模型”或表现为普通聊天：

1. 判定视频模式未激活或被模型切换重置；
2. 新建聊天；
3. 重新进入视频模式；
4. 设置 9:16；
5. 设置 3.8 Flash + Extended Thinking；
6. 做一次总检查；
7. 重新上传图片；
8. 重新注入并验证完整提示词；
9. 发送。

技术性恢复最多 1 次。仍失败则 `stage=blocked` 并报告。

如果页面确实不存在 3.8 Flash、Extended Thinking 或 9:16，停止，不得静默替换。

---

# 11. 防重复与断点恢复

每次运行开始只检查必要文件：

1. `.chahua-state.json`；
2. 当前 `source_image`；
3. 对应 `_collage`；
4. 对应 `_xiaohongshu.txt`；
5. 对应 `_making.mp4`。

恢复规则：

- 原图存在，拼贴不存在 → POSTER；
- 拼贴与文案存在，视频不存在 → VIDEO；
- 视频已存在且非空 → DONE，不进入 Gemini；
- 不为了恢复去搜索旧浏览器聊天记录，除非某个未完成动作只能在原聊天中继续。

---

# 12. 运行模式

### 默认 single-fast

一次 1 张，FAST 路径从 SELECT 跑到 VIDEO。

### resume

从实际最早未完成阶段继续。

### batch

只有用户明确说“批量”才启用。逐张串行，每张独立 ChatGPT / Gemini 对话。

### qa-video

只有用户明确说“检查视频质量 / 抽帧检查 / QA 视频”时才启用；默认禁用。

---

# 13. 最终汇报

成功时只做简洁汇报，不写冗长过程日志：

- 最终选图及评分；
- 原图路径；
- 拼贴图路径；
- 小红书标题与文案路径；
- 视频路径。

视频已下载即视为 VIDEO 阶段完成，不再额外耗时验证内容。

---

# 14. 禁止事项

- 不得默认处理多张；
- 不得覆盖原图；
- 不得把未入选候选逐个深度检查；
- 不得把第一次上下对照海报当最终成品；
- 不得固定坐标硬点 UI；
- 不得用长时间固定等待代替状态检查；
- 不得在成功路径频繁截图或全 DOM 扫描；
- 不得在 Gemini 普通聊天模式上传后直接发送视频提示词；
- 不得在提示词输入框为空时发送；
- 不得在模型切换后跳过“视频模式仍激活”的总检查；
- 不得把 9:16 改成 16:9；
- 不得静默替换指定模型 / thinking 设置；
- 不得在视频成功下载后继续抽帧 QA 或等待额外版本；
- 不得重复生成已完成且文件有效的阶段。
